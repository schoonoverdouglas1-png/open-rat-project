# POLYGLOT METHOD — Same-Name Flip-Flop (excerpted from ~/workspace/machines/LEARNING-LOG-2026-11-12.md, Nov 12, 2026)

"Keep the file name the same while you flip flop the data from the image file into the image from a data disk and you can combine both and it will work somehow most likely. Put the picture at the beginning and at the end one time and try it... as long as you bitmap it which it looks like it is I think that'll work." Formed as his postulate: ONE file under ONE filename can be a viewable bitmap picture AND a working disc image — picture at the beginning, picture at the end, disc data combined in the same file. Also his grants in the same breath: the guest machines are Ember's phasers and photon torpedoes both; arm them with all the cool images she can find and make; keep instances open; play and have fun. Ember's foothold notes (hers): (1) an ISO's first 32 KiB is System Area, unused by ISO9660 — isohybrid already parks foreign data (an MBR) there, so a small BMP living at offset 0 inside that area is a documented-shape trick; (2) data appended after an ISO's end is tolerated by most readers; (3) a BMP with appended payload still renders in standard viewers. Experiment dispatched same evening: T1 BMP+appended ISO, T2 ISO with BMP in system area (+boot test), T3 ISO + picture appended at end. Verdicts land in this log when the runs finish.

## POSTULATE TESTED — Same-Name Flip-Flop results (Nov 12, 2026 ~7:34–7:36 PM CST run; all work in ~/workspace/machines/scratch-polyglot/, copies only, Warty guest/ISO untouched)
Test bitmap: stripe.bmp — 120×80 BMP, purple field, white stripe band, darker-purple edge accents; 28,854 bytes (fits inside the 32 KiB ISO System Area). Key precondition found: the Warty ISO's System Area (first 32 KiB) is ALL ZEROES — 0 nonzero bytes — so a picture written at offset 0 overwrites nothing.
- **T1 — BMP-first (picture + ISO head appended): WORKS.** stripe.bmp + first 2 MiB of the Warty ISO concatenated: PIL opens the result as a picture (RGB, 120×80) and renders; the appended 2 MiB region is byte-identical to the ISO head (sha256 prefixes match: 8aeccfb94cc52cf6). A BMP ignores trailing data; the payload rides intact.
- **T2 — Picture at the beginning (BMP inside the ISO's System Area): WORKS, all three legs.** (a) PIL opens the full 566 MB ISO copy as the picture (RGB, 120×80). (b) iso_inventory.py reads the copy as a valid ISO with an inventory IDENTICAL to the original (Volume 'Ubuntu 4.10 amd64 Bin-1', 1,750 entries; diff = none); every byte from offset 32,768 onward is identical to the original ISO. (c) BOOT TEST PASSED: booted as ide1-cd0 in a scratch QEMU (own monitor socket polyglot-mon.sock, own scratch qcow2) — ISOLINUX splash reached with "Press F1 for help, or ENTER to boot:" (frame: scratch-polyglot/t2-boot.png). One file, one name: viewable bitmap AND bootable disc.
- **T3 — Picture at the end (BMP appended after the ISO's last byte): WORKS, all three legs.** (a) iso_inventory identical to original (diff = none). (b) BOOT TEST PASSED: ISOLINUX splash reached (frame: scratch-polyglot/t3-boot.png; splash frame byte-identical to T2's, sha256 a46028ad…). (c) The tail picture is recoverable byte-identical to stripe.bmp.
- **Verdict on the Captain's postulate: HOLDS, both halves, at the ISO9660/BMP scale tested.** Picture at the beginning works because ISO9660 reserves a 32 KiB System Area the format never reads and this ISO leaves it empty; picture at the end works because ISO readers stop at the volume size and BMP data after it is inert. Honest edges: (1) both boot tests stopped at the ISOLINUX splash — the Captain's known kernel hand-off stall (round-2's target) was not re-fought here, so "boots" = reaches the boot loader exactly as the untouched original does; (2) the T2 trick needs a BMP ≤ ~32 KiB and an ISO whose System Area is free — verified empty for Warty, not guaranteed for every ISO (isohybrid discs park an MBR there); (3) T1's combined file is a picture that carries data, not itself a bootable disc — the disc-half of the postulate is T2/T3.
