# Android as a Computer — Access Routes for a Remote Linux Agent

**Device/scenario assumed:** owner's own Pixel 7 Pro (Tensor G2), Android 17, locked bootloader, **no root**. The "computer" that wants access is a **remote Linux agent on a separate Linux VM — internet only, NOT on the phone's LAN**. That last constraint eliminates several routes outright and is flagged per route as **Remote-VM verdict**.

**Reading note on dates:** sources were read 2026-11-09. Several facts are fast-moving and version-sensitive (scrcpy, Shizuku, Android 17 QPR features); version numbers below are as reported by the cited sources on that date.

## Summary

- **Only two families of routes can reach the phone from an internet-only remote VM at all:**
  1. **A mesh VPN the owner installs on both ends (Tailscale)** carrying Termux SSH (and, fragilely, ADB) — no port-forwarding, works through NAT/CGNAT; and
  2. **Vendor-relay remote-support apps** (TeamViewer/AnyDesk/AirDroid) — internet-native by design, but built for a *human* looking at a GUI, with per-session consent prompts on Android, and no shell/API an agent can drive.
- **Everything else is local by design:** ADB (USB or same-Wi-Fi), scrcpy (rides ADB), Shizuku/LADB (on-device), proot distros (on-device), and the AVF Debian VM (reachable only from the phone itself).
- **The composable winning stack is: Termux (F-Droid build) + key-only `sshd` on 8022 + Tailscale on phone and VM.** Add **Shizuku + `rish` inside Termux** if the agent also needs ADB-shell-level Android commands — the SSH session can then call `rish -c …`. The owner must restart Shizuku after every reboot.
- **Pixel 7 Pro hard limits:** no DisplayPort Alt Mode → **no wired external display / Android desktop mode** (that's Pixel 8+), regardless of Android 17. The **Linux Terminal (AVF Debian VM) should be available in principle** — Tensor chips support the non-protected VMs it needs and the Terminal package has been observed on a Pixel 7 Pro — but the owner must confirm the *Linux development environment* toggle actually exists on their build.
- **Do not** port-forward 8022/5555 to the public internet, do not use Ubuntu's `scrcpy` 1.25 on Android 17 (it demonstrably fails), and do not root/unlock the bootloader for this use case — nothing in the mission needs it, and unlocking wipes the phone.

## Findings

### 1. Termux + OpenSSH server (`sshd`, port 8022) — over LAN and over Tailscale

**What it is / access given.** Termux is a terminal emulator + Linux userland that runs as an ordinary Android app, no root. It gives a real shell with `pkg`/`apt`-style packages (Python, git, OpenSSH, tmux, compilers) in Termux's private directory (`/data/data/com.termux/files`), plus shared storage only after the owner runs `termux-setup-storage` and grants the permission (symlinks under `~/storage`). It is **not** Android OS access: no other apps' private data, no system settings, no `sudo`/`su` — Termux's user is an app UID. Sources: Termux install/usage guides, index — https://tomorrowdesk.com/info/termux ; https://h5.2113.net/guides/termux-commands.html

**Install correctly (owner, on phone).** Install Termux from **F-Droid or the official GitHub releases only**, and install all Termux add-ons (Termux:API, Termux:Boot, etc.) from the *same* source — the builds are signed differently and mixing them breaks add-ons. The long-standing Google Play build was deprecated/separately signed (project announcement, termux-app discussion #4000); some 2025–26 sources mention a resumed, separate Play branch — either way F-Droid/GitHub remains the project's recommended channel. Stable F-Droid line reported as 0.118.3 (May 2025). Sources: index — https://williamlodge.github.io/termux-field-guide/ ; https://pinggy.io/amp/blog/host_website_on_android/

**SSH server setup (owner, in Termux).**
```
pkg update && pkg install openssh
passwd            # or, better, install a public key and disable password auth
whoami            # note the u0_aXXX username
sshd              # listens on 8022
```
Port **8022** is the default because an unprivileged app cannot bind ports <1024. From a computer on the same LAN: `ssh -p 8022 <whoami>@<phone-LAN-IP>`. Stop with `pkill sshd`. Sources: index — https://termuxtools.com/ssh-server-termux-setup-guide-2/ ; Termux-wiki-derived guide https://wiki.emberlife.com/index.php?title=Termux&action=pandoc&format=pdf (note: the Termux Wiki itself has been frozen since April 2026 per https://h5.2113.net/guides/termux-commands.html , so prefer the app/GitHub docs for version-sensitive facts).

**Keeping it alive — the real work.** Android actively kills background Termux processes. Mitigations, all owner-applied, none perfect:
- Settings → Apps → Termux → Battery → **Unrestricted**.
- `termux-wake-lock` (needs Termux:API) before starting `sshd`; released on app kill/reboot.
- Android 12+ **Phantom Process Killer** (32 phantom-process cap; symptom `[Process completed (signal 9)]`): on Android 14+ enable Developer options → *Disable child process restrictions*; on 12L/13 the documented fix is a one-time `adb shell settings put global settings_enable_monitor_phantom_procs false` from a computer.
- Optional persistence: `pkg install termux-services` + `sv-enable sshd` (runit supervision), and/or a Termux:Boot script that takes a wake-lock and starts `sshd`. Even stacked, sources stress there is *no single guaranteed fix* — memory pressure can still kill it.
Sources: index — https://www.bigiron.cc/guides/termux-services-that-survive-the-phantom-process-killer ; https://h5.2113.net/guides/termux-commands.html

**Remote-VM verdict.**
- **Over LAN: NO for this scenario.** LAN SSH only works for a client on the same Wi-Fi; the phone's `192.168.x.x` address is not routable from the internet, and the phone is behind NAT/CGNAT.
- **Over Tailscale: YES — this is the recommended remote path.** Owner installs the Tailscale Android app, signs phone and the Linux VM into the same tailnet, and approves both devices. Tailscale is a WireGuard mesh: each device gets a stable `100.64.0.0/10` address, NAT traversal is automatic (STUN/hole-punching, with encrypted DERP relay fallback), and **no router port-forwarding is needed**. Termux's `sshd` binds all interfaces, so it becomes reachable at the phone's Tailscale address: `ssh -p 8022 u0_aXXX@100.x.y.z`. A worked Termux+Tailscale guide reports exactly this result — "an SSH shell … into the phone from any network, addressed by the phone's 100.x.y.z Tailscale IP." Sources: index — https://ai-release.org/guides/kak-podklyuchit-staryy-android-smartfon-bez-root-k-tail_en.html ; Tailscale mechanics https://selfhostedworld.com/guides/what-is-tailscale
- **Blockers/caveats:** (a) Android allows **only one active VPN (`VpnService`) per user/profile** — Tailscale occupies that slot, so the owner cannot run another VPN app simultaneously (index — https://bayton.org/android/android-enterprise-faq/multiple-vpn-connections/ ); (b) Tailscale must be *connected* and Termux/`sshd` *alive* (see keep-alive above) at the moment the agent connects — a reboot or process kill means the owner must relaunch Termux/`sshd` (Termux:Boot reduces but does not eliminate this); (c) use **key-only auth** (disable password login in `$PREFIX/etc/ssh/sshd_config`), restrict the tailnet ACL so only the agent VM can reach the phone, and set node key expiry — the tailnet, not the LAN, is now the trust boundary. **Never** substitute public port-forwarding of 8022 for this.
- **Reversibility:** excellent. `pkill sshd`, uninstall Termux/Tailscale, remove the VM from the tailnet, delete authorized keys. Nothing system-level is modified.

### 2. ADB — USB and Wireless Debugging; `adb shell` limits without root

**What it is.** Official Google tool: client on the workstation, `adbd` daemon on the phone. Gives a Unix shell plus `install`/`uninstall`, `push`/`pull`, `logcat`, `screencap`/`screenrecord`, `pm`/`am`/`settings`/`dumpsys`, input injection. Source: verified live — https://developer.android.com/tools/adb?authuser=0

**Owner steps (phone).** Settings → About phone → tap **Build number 7×** → Developer options → enable **USB debugging** (for USB) and accept the RSA "Allow USB debugging?" dialog per computer (tick *Always allow from this computer* only for trusted machines). Revocation is one tap: Developer options → *Revoke USB debugging authorizations*.

**Wireless Debugging (Android 11+).** Developer options → **Wireless debugging** → *Pair device with pairing code* (or QR) → on the workstation `adb pair <ip>:<pairing-port>` with the 6-digit code, then `adb connect` to the *different* connect port shown on the Wireless debugging screen. Official requirements, verified live: **workstation and device must be on the same wireless network**; pairing is one-time (device stays paired until forgotten/revoked) and auto-connects on the same network. Source: https://developer.android.com/tools/adb?authuser=0
**Android 17 change:** Android 17 + Platform-Tools **adb 37.0.0** introduces **ADB Wi-Fi 2.0** — new mDNS stack, auto-connect when the phone joins a *trusted* wireless-debugging network, and `adbd` automatically disables Wi-Fi ADB on untrusted networks (Google reports +32% auto-connect success, +66% connection speed for 90% of connections). Requires Android 17, Platform-Tools 37.0.0 and same Wi-Fi. Sources: verified live — https://developer.android.com/tools/adb?authuser=0 ; https://developer.android.com/blog/posts/introducing-fast-and-reliable-wireless-debugging-with-android-debug-bridge-adb-wi-fi-2-0?hl=en&authuser=01
**Legacy `adb tcpip 5555`** (USB once, then `adb connect <ip>:5555`) still works on Android 11+ but is the Android ≤10 flow: RSA-authenticated but **unencrypted** — trusted networks only, and it dies at reboot.

**Limits without root — important.** `adb shell` runs as the **`shell` user, UID 2000** — above normal apps, far below root:
- **Cannot** read other apps' private data: `/data/data/<pkg>` returns *Permission denied* (app sandbox + SELinux). `run-as` works **only for debuggable apps** (i.e., the developer's own debug builds, not installed production apps).
- **`adb root` fails on this phone**: *"adbd cannot run as root in production builds"* — retail Pixels have `ro.secure=1` / `ro.debuggable=0`. Likewise `adb remount` (read-write `/system`) fails.
- What shell *can* do is still broad: install/remove apps (with on-phone confirmation for some operations), grant/revoke many permissions, change many `settings` values, `pm disable`/`uninstall --user 0` (per-user, reversible — not real system-app removal), screenshots, logs, `dumpsys` diagnostics.
Sources: index — https://codemia.io/knowledge-hub/path/adb_access_denied_to_data_folder ; https://www.tutorialpedia.org/blog/how-can-one-pull-the-private-data-of-one-s-own-android-app/

**Remote-VM verdict: NO, natively.** USB requires a cable plugged into *a computer next to the phone* — an internet-only VM has no USB path at all. Wireless Debugging requires the **same Wi-Fi network** by design (official docs, above); there is no internet mode. The only bridges are: (i) a *local* trusted computer acting as relay (outside this scenario), or (ii) **ADB over the Tailscale address** — one worked guide demonstrates pairing/connecting to the phone's `100.x` address and getting an ADB shell "from any network," but this is not an officially documented ADB mode: mDNS auto-discovery doesn't carry it, pairing/connect ports rotate per session, and Wireless Debugging must be re-enabled by the owner (Android 17's Wi-Fi 2.0 auto-connect is tied to trusted *Wi-Fi LANs*). Treat ADB-over-Tailscale as **possible-but-fragile, session-by-session, owner-assisted** — never the foundation. Sources: index — https://ai-release.org/guides/kak-podklyuchit-staryy-android-smartfon-bez-root-k-tail_en.html ; https://www.ros-developer.com/2026/10/12/scrcpy-adb-android-wifi/ (port rotation, wireless debugging turns off when leaving the Wi-Fi network).

**Risks/reversibility.** An authorized ADB host has deep control (install apps, read logs/storage it can reach, inject input) — authorize only the owner's machines, revoke when done, turn Wireless Debugging **off** when not in use. Fully reversible via revoke + toggles off.

### 3. scrcpy — screen mirroring/control over ADB

**What it is.** Genymobile's open-source tool: mirrors the phone's screen (video + audio) to a window on the computer and injects keyboard/mouse/touch via ADB. **No root, no app installed on the phone** (a temporary server is pushed via ADB), works on Linux/Windows/macOS, Android 5.0+ (audio forwarding Android 11+). Current version per the official README: **v5.0.1** (v5.0, Oct 2026, added GPU hardware decoding). Source: index — https://github.com/Genymobile/scrcpy/blob/master/README.md?plain=1

**Version trap on Android 17 — confirmed failure.** Ubuntu 24.04's `apt install scrcpy` gives **scrcpy 1.25 from 2022**. Demonstrated on a Pixel 8 Pro running Android 17, 1.25 dies with:
`NoSuchMethodException: android.content.IClipboard$Stub$Proxy.addPrimaryClipChangedListener…` / `android.view.SurfaceControl.createDisplay…` → *Device disconnected* — scrcpy uses internal Android APIs that change between releases, so old clients break on new Android. **Fix:** install the current release tarball from Genymobile's GitHub (the README says GitHub is the *only* official source), verified in that walkthrough as scrcpy 5.0.1. Watch the **two-ADBs trap**: the release bundle ships adb 37 while Ubuntu's `adb` package is 34; running both causes *"adb server version doesn't match this client; killing…"* loops and re-authorization prompts — standardize on one `adb`. Source: verified live — https://www.ros-developer.com/2026/10/12/scrcpy-adb-android-wifi/

**Owner steps.** Same as ADB: enable USB debugging and authorize the host (USB), or enable Wireless Debugging + pair (Wi-Fi). Nothing to install on the phone. Useful flags: `scrcpy --tcpip` (one-command cable→Wi-Fi switch), `-m 1024 -b 4M` for slow links, `-S` (phone screen off while mirroring), `--record`.

**Remote-VM verdict: NO as a primary route.** scrcpy has no transport of its own — it inherits ADB's, so USB/same-Wi-Fi limits apply verbatim; over ADB-over-Tailscale it would inherit that fragility too. There is also a practical agent problem: scrcpy renders an interactive GUI window — a headless Linux VM agent would need a virtual display and a way to "see" and click, at video bandwidth, which is a poor substitute for a shell. Use scrcpy **locally, human-in-the-loop**, when a GUI is genuinely needed (e.g., tapping through an app that has no CLI/API).

**Risks/reversibility.** Whoever holds the authorized ADB connection + scrcpy effectively holds the unlocked phone's screen — same trust as ADB. Nothing persists on the phone; revoke ADB authorization to end it.

### 4. Shizuku + `rish`, and LADB — ADB-level privileges on-device, without root

**Shizuku — what it is.** An open-source (RikkaApps) service that starts a privileged process with **ADB (`shell`, UID 2000) identity** — or root identity *only if the phone is rooted and it's root-started* — and brokers Android system APIs to apps the owner explicitly authorizes, plus a shell via **`rish`**. It does nothing alone; it's a privilege bridge for other apps/terminals. Current release per secondary sources: **13.6.0 (May 2025)**. Sources: index — https://github.com/zex808/hacktricks/blob/HEAD/src/mobile-pentesting/android-app-pentesting/shizuku-privileged-api.md ; https://h5.2113.net/apps/shizuku.html

**Owner steps + the reboot limit (official manual).** Three start modes: (1) **via Wireless debugging** (Android 11+, no computer): enable Developer options + Wireless debugging, pair Shizuku once via its notification + the 6-digit code, tap *Start*; (2) **via a computer's ADB** (the manual's path for Android ≤10, works later too); (3) root — not applicable. Official manual, verified live: *"Due to system limitations, the startup steps need to be performed again after each reboot"* for both non-root modes. Source: https://shizuku.rikka.app/guide/setup/?night=1
*Version-sensitive update:* secondary coverage of 13.6.0 says it (a) replaced the manual's `start.sh` computer command with a `libshizuku.so` command you copy from the app's *View command* (the official manual still shows the old command — follow the app, not the manual, on 13.6.0), and (b) can **auto-start without root on Android 13+ when the phone rejoins a trusted WLAN** (it re-enables wireless debugging at boot). Treat (b) as a convenience that *may* work on the owner's home Wi-Fi, not a guarantee — the planning assumption remains "owner taps Start after each reboot." Source: index — https://h5.2113.net/apps/shizuku.html

**`rish` — why it matters for a remote agent.** In Shizuku → *Use Shizuku in terminal apps*, export `rish` + `rish_shizuku.dex` into Termux, set `RISH_APPLICATION_ID=com.termux` (on Android 14+ the dex must be made read-only, `chmod 400`), and `./rish` drops into a shell running as UID 2000; `rish -c '<cmd>'` runs one-off ADB-shell commands (`pm`, `am`, `settings`, `dumpsys`, appops, etc.). **Composition:** a remote agent that has SSH'd into Termux (§1) can invoke `rish -c …` and thereby gets *both* the Termux userland *and* shell-level Android commands in one channel — the strongest no-root remote combination available. It inherits Shizuku's limits: dies at reboot, and shell UID still cannot read other apps' `/data/data` or touch the system partition. Sources: index — https://deepwiki.com/timschneeb/awesome-shizuku/4-the-rish-shell ; https://shizukudownload.com/rish/

**LADB — the alternative, and the conflict.** LADB is a paid Play Store app that bundles an ADB server and connects it to the phone's *own* wireless-debugging service, giving the owner a local ADB shell with no computer at all. Setup is fiddly: split-screen LADB + Settings, because Android invalidates the pairing dialog if it's dismissed; enter the pairing code/port in LADB and keep both windows open until pairing completes. **Direct conflict, from LADB's own listing: "LADB is sadly incompatible with Shizuku… if you have Shizuku installed, LADB will usually fail to connect properly. You must uninstall it and reboot to use LADB."** Troubleshooting for most LADB errors is likewise: clear app data, remove all Wireless Debugging pairings, reboot. Source: index — https://play.google.com/store/apps/details?id=com.draco.ladb&hl=en-us&gl=us
**Verdict on LADB for this mission:** it gives the *owner holding the phone* a shell — it exposes **no remote interface**, so it does nothing for a remote agent, and choosing it *costs* you Shizuku+`rish`. **Pick Shizuku, skip LADB**, unless the owner specifically wants a standalone on-phone ADB shell and no Shizuku apps.

**Remote-VM verdict (Shizuku/rish): indirect YES, via §1 only.** Shizuku itself opens no network listener for the agent; it becomes remotely useful solely because Termux SSH can call `rish`. Blocker: after every phone reboot, Shizuku is dead until the owner restarts it on the phone (subject to the 13.6.0 trusted-WLAN auto-start caveat).
**Risks/reversibility:** any app the owner authorizes in Shizuku runs as shell — authorize sparingly, revoke in Shizuku's app list. Fully reversible: stop Shizuku / reboot / uninstall; nothing is flashed.

### 5. Android desktop / external display, and the built-in Linux Terminal (AVF Debian VM)

**5a. External-display desktop mode — NOT on Pixel 7 Pro.** Android's connected-display desktop windowing (taskbar, freeform windows) became generally available in **Android 16 QPR3** for supported Pixel/Samsung phones — but it rides on **DisplayPort Alt Mode over USB-C, which starts at Pixel 8**. Google's own Pixel Help wires this up under the heading *"Connect your phone to a display device (Pixel 8 and later)"* (verified live — https://support.google.com/pixelphone/answer/2865484?hl=en ). First-hand confirmation: a Pixel 7 Pro owner notes desktop mode "requires hardware that my Pixel 7 Pro simply didn't have. DisplayPort Alternate Mode over USB-C — not something the 7 series supports" (index — https://pelica.net/en/my-phone-my-desktop-sort-of ). **No cable, hub, dock, or Android 17 update changes this** — the 7 Pro's USB-C port carries charge + data only. The only display-out left is wireless **Cast** (mirroring to a Chromecast-type receiver — viewing, not a desktop, and not agent access). This route is also inherently *local and physical* (monitor + keyboard at the phone), so it never served the remote-VM scenario anyway.

**5b. Linux Terminal app / AVF — a real Debian VM, local to the phone.** Since Android 15/16 (Pixel-first), Developer options → **Linux development environment** enables Google's *Terminal* app, which downloads a ~500–600 MB Debian image and boots it as a **virtual machine under the Android Virtualization Framework (AVF / pKVM on crosvm)** — its own Linux kernel, `apt`, systemd, GPU-forwarded GUI apps on newer Pixels — categorically different from Termux/proot. AVF itself is Google's framework for isolated (protected) VMs on ARM64. Sources: index — https://source.android.com/docs/core/virtualization (AVF overview via search); https://www.makeuseof.com/turned-android-into-linux-desktop-tool-buried-android-16/ ; Terminal package observed on a Pixel 7 Pro (Android 16) — https://sysapps.bayton.org/packages/com.android.virtualization.terminal
**Will it run on *this* Pixel 7 Pro / Android 17? Probably yes — owner must verify.** The Terminal needs a chip that can run **non-protected VMs**: Google Tensor qualifies, Snapdragon (as of mid-2026) does not — the Pixel 7 Pro is Tensor G2 (index — https://andronix.app/blog/android-linux-terminal-vs-termux ). Android 17 QPR coverage likewise puts Terminal eligibility at "Pixel 7 or newer" (index — https://android.gadgethacks.com/news/android-17-qpr1-beta-5-linux-terminal-app-features-resolution-themes-explained/ ). The definitive test costs the owner 30 seconds: **if Settings → System → Developer options → *Linux development environment* is present, the path exists on that build; if it's absent, no setting can add it** (verified live, first-hand Android 17 guide — https://raw.githubusercontent.com/ferrumclaudepilgrim/claude-code-android/master/docs/avf-guide.md ).
**What access it gives — and doesn't.** Inside the VM the agent/owner is effectively root-able (`sudo`) on a genuine Debian 13 system — the *least* constrained Linux in this report, and the *most isolated*: the VM is **not a shell into Android**. It sees Android only through `/mnt/shared` (shared storage) and, if the owner enables Wireless Debugging and pairs from inside the VM, through ADB to the host phone (battery, `dumpsys`, logcat, input, screenshots were all demonstrated from inside the VM on Android 17). It has no native access to Android app data, sensors-as-Linux-devices, or USB passthrough. Source (Bayton): "It is not a shell into Android"; AVF guide as above.
**Hardening if used (from first-hand Android 17 testing):** the VM's `droid` user has a **known default password and passwordless sudo**, no firewall, and OpenSSH is *installed but not running* — before enabling SSH inside the VM (`sudo systemctl enable --now ssh`), change the password and set `PasswordAuthentication no` / key-only. Keep keys in `~/.ssh` inside the VM, never on `/mnt/shared` (any app with storage access could read them there).
**Persistence:** Android kills the VM when the screen turns off; Android 17 adds Terminal Settings → Advanced → **Keep awake** (timer up to 1 day, with an explicit battery warning). Long jobs should run under `tmux`/`nohup` regardless. The VM's IP changes every boot, and *"the VM is on a virtual network not directly reachable from the internet. Only the Android host can reach it"* (Terminal's *Port control* setting governs which VM-opened ports the host may reach).
**Remote-VM verdict: NO direct route.** Because only the Android host can reach the VM, an internet-only agent cannot SSH into it as-is. Options are (i) run the agent *inside* the VM (a local-agent model — the VM then reaches the internet itself, and can even ADB-bridge to the host phone as above), or (ii) establish an *outbound* tunnel from inside the VM (its TUN device makes a VPN client conceivable) — plausible but **not verified in any source found**; do not promise it. For *remote-agent-into-phone*, Termux (§1) remains the proven path; the AVF VM is best framed as a clean, disposable, strongly-isolated Linux sandbox *on* the phone.
**Reversibility:** excellent — toggle the developer option off / Terminal Settings → Recovery → *Reset to initial version* wipes the guest; Android is untouched.

### 6. Linux-on-Android: Termux `proot-distro`, UserLAnd, Andronix

**What they are.** All three run a conventional glibc distro userland (Debian, Ubuntu, Arch, Kali, Fedora…) under **PRoot** — user-space syscall translation that *fakes* a chroot/root inside an app sandbox. **No new kernel, no VM, no root.** You get the distro's `apt`/`dnf` and desktop (via Termux:X11 or VNC), on Android's kernel, as an unprivileged app.
- **`proot-distro`** (Termux add-on): the maintained, free, CLI-first option — current release reported **5.1.1 (2026-05-24)**; `pkg install proot-distro`, `proot-distro install debian`, `proot-distro login debian`. Source: index — https://cosyra.com/guides/android-linux-container.html
- **UserLAnd:** the friendliest wizard (distro + SSH/VNC built in), but its **GitHub code/releases have been frozen since v2.8.3 in October 2021** per multiple 2026 comparisons (its Play listing still receives store updates — a discrepancy worth noting; the upstream project is effectively unmaintained). Sources: index — https://cosyra.com/guides/android-linux-container.html ; https://andronix.app/blog/userland-alternative
- **Andronix:** a guided/commercial layer — historically scripts on top of Termux, and **Andronix 10.1 (Oct 2026)** now also runs distros/desktops (XFCE/LXQt/MATE/KDE) inside its own app on arm64/Android 8+. Same PRoot ceiling either way. Source: index — https://andronix.app/blog/userland-alternative

**Limits (shared, structural).** Slower than native Termux (PRoot intercepts syscalls); **no Docker** — Android denies unprivileged apps the kernel namespaces/cgroup/overlayfs a container runtime needs; likewise **no Snap/Flatpak, no VPN clients, no USB hardware access** inside the distro (Andronix's own limitation list); GUI is VNC/X11 at phone resolutions; and the **Phantom Process Killer applies unchanged** — long builds die when Android reaps the host app. Sources: index — https://cosyra.com/guides/android-linux-container.html ; https://andronix.app/blog/userland-alternative
**Owner steps.** Install Termux (F-Droid) → `proot-distro` as above; or install UserLAnd/Andronix and follow the wizard, grant storage, expect 4–8 GB for a desktop Ubuntu.
**Remote-VM verdict: inherits Termux.** A proot distro adds **no network listener of its own**; the remote agent reaches it exactly as in §1 — SSH into Termux over LAN/Tailscale, then `proot-distro login …` inside that session. If Termux SSH is down, the distro is unreachable, full stop.
**Risks/reversibility.** Low risk (app-sandboxed, fake root is not real root — a proot "root" process still cannot escape the app UID). Fully reversible: `proot-distro remove <distro>`, uninstall the app.

### 7. Remote-support apps (TeamViewer, AnyDesk, AirDroid) and MDM

These are the only routes besides Tailscale that **traverse the internet by design** (vendor relay clouds punch through NAT for you) — and they are designed for a **human support technician with a GUI client**, not for a programmatic Linux agent.

**TeamViewer QuickSupport / Host.** Owner installs QuickSupport (+, for control on devices without a manufacturer add-on, the **Universal Add-on** accessibility service). QuickSupport rules, from TeamViewer's own listing/KB: the app must be **open in the foreground**, the owner shares an ID/session code, and must **accept the connection request every time** — "without your explicit permission, the connection can't be established." Host is the unattended variant, **but TeamViewer's KB states unattended access is *not* available when Host relies on the Universal Add-on — it will always ask the end user for confirmation.** Some devices are screen-share-only. Gives: screen view/control (where the add-on works), file transfer, device info — **no shell, no ADB, no API for an agent**; sessions run through TeamViewer's cloud under a TeamViewer account/license (mobile-to-mobile free sessions are time-limited per TeamViewer). Sources: index — https://play.google.com/store/apps/details?id=com.teamviewer.quicksupport.market&hl=en-us ; http://teamviewer.com/en-in/global/support/knowledge-base/teamviewer-classic/mobile/android/universal-add-on-for-android/?language-switched=true
**AnyDesk.** Similar model: AnyDesk app + a **control plugin** (universal `ad1`) enabled under Settings → Accessibility is required for input — without it, view-only, because Android doesn't let apps inject input by default. Unattended Access (password) exists, **but AnyDesk's own help warns that on Android 10+ a system screen-sharing/recording prompt appears at session start and "in most cases must be manually accepted by someone physically present," even with unattended access configured.** Gives GUI control + file transfer, no shell. Source: index — https://help.anydesk.com/en/android
**AirDroid Personal (+ AirMirror/Remote Support).** Account-centric suite: file transfer/management, notifications/SMS on PC, screen mirroring and remote control without root via the **AirDroid Control Add-on + accessibility permission** (Android 7+), or a one-time **Non-Root setup from a PC over USB — which must be repeated after every phone restart**. Works over the internet via AirDroid's account cloud; the **free tier caps remote (non-LAN) data at 200 MB/month** and locks some features (e.g. remote camera) behind Premium. Broad permission surface (files, camera, screen, accessibility) held by a third-party cloud account is the price. Sources: index — https://www.airdroid.com/guide/airdroid-personal/ ; https://play.google.com/store/apps/details/AirDroid_File_Remote_Access?id=com.sand.airdroid&hl=en_ZA
**Remote-VM verdict for all three:** a *human* at a TeamViewer/AnyDesk/AirDroid desktop client could connect from anywhere — but a **headless Linux agent cannot meaningfully drive these GUI clients** (no supported CLI/API for autonomous control was found), and the Android-side consent/capture prompts mean "unattended" is unreliable by platform design. Appropriate use: an occasional, owner-present, human-operated support session. Not an agent access route.
**MDM / Android Enterprise.** A different animal: policy management, not interactive access. A Device Policy Controller can inventory, enforce restrictions, push apps, locate/lock/wipe, and (device-owner only) remotely reboot — it provides **no shell and no live screen control** for an agent. The modes matter for a personal phone: on a **personally owned device, only a work profile (profile owner) is available — management is confined to the work profile; personal apps, photos and messages are explicitly out of the MDM's reach.** Full **device-owner** control requires the phone to be **factory-fresh / factory-reset and provisioned at setup** — i.e., wiping the owner's phone to enroll it, and handing a third-party server standing policy authority over it. Sources: index — https://developer.android.com/work/dpc/device-management?hl=en&authuser=0 ; https://www.manageengine.com/mobile-device-management/android-management.html?it_securty_lp
**Verdict:** grossly disproportionate for one owner + one agent. Do not recommend MDM here.
**Reversibility:** support apps — uninstall + revoke the accessibility service + close the vendor account session; MDM — unenroll (work profile removal is clean; device-owner removal generally means factory reset).

### 8. What is NOT possible without root or a custom ROM

With a locked bootloader and stock Android 17, **none** of the routes above — individually or combined — can:

- **Be root (UID 0).** No `su`, no `adb root` (refused on production builds), no read-write remount of `/system` or other verified partitions, no kernel/module changes, no SELinux policy changes. Every "shell" in this report is UID 2000 (ADB/Shizuku) or an app UID (Termux/proot) or a *guest* root that exists only inside the AVF VM.
- **Read other apps' private data.** `/data/data/<other-pkg>`, app-private external dirs, and credential stores stay sealed by the sandbox + SELinux for ADB, Shizuku, Termux, and the VM alike. `run-as` helps only with debuggable (own debug) builds. Likewise, data encrypted before first unlock / behind the lock screen is not reachable by any of these routes — none of them bypasses the owner's lock screen or extracts a device-encrypted backup.
- **Persist like a system service.** No route can guarantee survival across reboot + process reaping without owner action: Shizuku/LADB and `adb tcpip` die at reboot; Termux `sshd` needs wake-lock/battery exemptions and can still be killed; wireless debugging turns itself off on network changes/untrusted networks. There is no no-root equivalent of a systemd unit running as a privileged user from boot.
- **Run real containers / system-level networking on Android itself.** No Docker (kernel namespaces/cgroups/overlayfs are locked to unprivileged apps), no binding ports <1024, no raw VPN/tunnel from inside proot, no USB device access from Termux/proot/VM. (Inside the AVF *guest*, Docker-adjacent tech like systemd-nspawn and OverlayFS do work — because it's a real VM kernel — but that Linux is a guest, not Android.)
- **Get hardware the phone doesn't have.** Wired video-out/desktop mode on the Pixel 7 Pro (§5a) is a hardware absence, not a software lock.
- **Silently or permanently remove system apps / change the OS.** ADB `pm uninstall --user 0` / disable is per-user and reversible, not deletion; flashing anything (custom recovery, ROM, kernel) requires **unlocking the bootloader, which factory-wipes the phone**, weakens verified boot, and is a one-way door in practical terms for banking/Play Integrity posture — explicitly out of scope for this mission, and unnecessary for every goal in §§1–6.
Sources: index — §§2/6 sources above, plus bootloader/root background https://en.androidayuda.com/android/Tutorials/How-to-root-and-unlock-the-bootloader-to-install-free-operating-systems/

## Safest-first recommendation

1. **Phase 1 — local proof (one evening, zero remote exposure).** Owner installs Termux from F-Droid, runs `pkg install openssh`, sets **key-only** auth (agent's public key in `~/.ssh/authorized_keys`, `PasswordAuthentication no`), starts `sshd`, and the agent connects from a machine on the same LAN (`ssh -p 8022`). Confirm the workflow is actually useful before adding any remote layer. Also flip Termux battery to Unrestricted, run `termux-wake-lock`, and (Android 14+) enable *Disable child process restrictions*.
2. **Phase 2 — make it remote, privately.** Owner installs Tailscale on the phone and the agent VM joins the same tailnet; tighten the tailnet ACL so *only* the VM can reach the phone; connect to `ssh -p 8022 <termux-user>@<phone's 100.x / MagicDNS name>`. **Never** port-forward 8022, never enable legacy `adb tcpip 5555` off a trusted LAN. Accept the availability model: if the phone reboots or Android kills Termux, access waits until the owner relaunches Termux/`sshd` (Termux:Boot + termux-services reduce how often).
3. **Phase 3 — Android-level commands, only if needed.** Owner installs Shizuku, starts it via Wireless debugging, exports `rish` into Termux; the agent's SSH session gains `rish -c 'settings …'` / `pm …` / `dumpsys …`. Budget for the ritual: **after every reboot the owner re-opens Shizuku and taps Start** (and re-checks Wireless debugging). Skip LADB entirely — it conflicts with Shizuku and adds nothing remote.
4. **Use locally, as needed:** current **scrcpy 5.0.1 from Genymobile GitHub** (never Ubuntu's apt 1.25) for human GUI tasks over USB/LAN; the **AVF Linux Terminal** — if the toggle is present on this build — as an isolated Debian sandbox for experiments the owner doesn't want touching Termux/Android, with its default password changed before any guest SSH is enabled.
5. **Avoid for this mission:** TeamViewer/AnyDesk/AirDroid as agent infrastructure (human GUI + vendor cloud + consent prompts), MDM enrollment (disproportionate, factory-reset for full control), proot desktops as a primary environment (slow, fragile), and any root/bootloader-unlock path (wipes the phone, weakens verified boot, buys nothing the mission needs).

**The one-sentence version for the owner:** *Install Termux and Tailscale, give the agent a key-only SSH login over the tailnet, optionally add Shizuku for Android commands — and expect to tap "Start" on Shizuku and occasionally relaunch Termux after reboots; that human-in-the-loop residue is the price of no-root, and it's a safety feature, not a bug.*
