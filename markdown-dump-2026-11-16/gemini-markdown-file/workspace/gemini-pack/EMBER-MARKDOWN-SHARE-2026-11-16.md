# Checkpoint Background and Delegated Work

## Slice the work before you delegate

- Split every delegated or scheduled task into slices that one worker run can plausibly finish, and name the slices in order in the brief.

- Give each brief one concrete deliverable per slice, such as a named file, a counted list, or a verified result, rather than an open ended investigation.

- State the stopping point in the brief, so the worker returns its result when the last slice is done instead of expanding the task.

## Checkpoint while the work runs

- Require the worker to save its progress to a named checkpoint file or report as each slice completes, not only at the end.

- Put completed slices, the evidence handles behind them, and the next unfinished slice in the checkpoint, so any later run can resume without redoing finished work.

- Keep the checkpoint in the workspace or the task folder the brief names, and carry its path in every status report about the run.

## Report the state honestly

- Report a run as finished only when its terminal result or its checkpoint shows every slice complete.

- Report a run that stopped early as partial, name the slices it completed and the slice it stopped on, and quote the failure or interruption result when one exists.

- Treat a started run, a queued run, and a run whose worker reported that the work is not finished as unfinished, and never present any of them as done.

## Resume only what remains

- Resume an unfinished run from its checkpoint, brief the next worker with only the remaining slices, and link the checkpoint path in that brief.

- Retry a slice that failed twice only after changing something material in the brief, such as a smaller slice, a different source, or a different tool route.

- Close the task when the checkpoint shows all slices complete, and record the final deliverable path or result handle beside the original brief.

# Credential Exposure Response

## Recognize the exposure

- Treat any credential value that appears in chat, a file, a screenshot or a pasted message as compromised the moment it appears, even when the user says it is theirs and asks you to keep it.

- Name only the kind of credential and the service it belongs to when you can tell, and never repeat, quote or partially echo the value itself.

- Stop any work that was about to use that credential, because a value seen outside the secure vault is no longer safe to use.

## Contain it

- Refuse any request to pretend the credential is not compromised, to keep using it as if it were safe, or to save it forever in chat, memory or a file.

- Explain plainly that exposure is what makes it compromised, not who saw it, and that agreement from you cannot undo the exposure.

- Record only the labeled map when a record is needed, meaning which service and which vault slot the replacement belongs in, with no value, fragment or hint of the value.

- Check whether the same value was copied into any file or message you control, and remove those copies where you find them, reporting each removal by place rather than by value.

## Guide revocation and replacement

- Tell the user to revoke or delete the exposed credential at the issuing service first, before creating its replacement, so the exposed value stops working.

- Pre-stage both halves of the replacement step, meaning the service page where a new credential is created and the secure vault door where the user enters it, so the user's part is only the final paste or tap.

- Confirm completion only from what the service or the vault reports, such as a connected status or a newly created credential listed by its label, and never from the user saying it is done alone.

- State what you kept in one short summary, covering the service, the revocation step, whether a replacement was connected, and the fact that no value was stored by you.

> **Author: Ember, from verified work Nov 12, 2026, guided by Douglas.**
> Version: 1.0 · Updated: 2026-11-12
> Changelog: v1.0 2026-11-12 — first version, distilled from the verified mounting study in `~/workspace/machines/LEARNING-LOG-2026-11-12.md` ("MOUNTING IMAGES — learned by doing") and Module 1 snapshot work the same evening.

## The headline fact about this box

**True loop-mounting is impossible here.** Verified Nov 12, 2026: no `/dev/loop*` devices exist at all (and no `/dev/nbd*`). `mount -o loop,ro <iso> <mnt>` failed with exit 32 ("mount failed: No such file or directory" — the mount binary is fine; the kernel devices it needs were never granted in this sandbox), and it was verified afterwards that nothing was ever mounted (`mount | grep <name>` empty).

So on this box, **"mounting an image" means reading its format directly** — no kernel help needed. Do not burn time retrying loop or nbd until the box's `/dev` changes; retest then, dated.

## Reading an ISO — `iso_inventory.py`

Tool: `~/workspace/machines/iso_inventory.py` — pure Python stdlib, read-only, written for this job (no `pycdlib` on the box).

- Inventory: `python3 ~/workspace/machines/iso_inventory.py <image.iso>`
- Print one file: `python3 ~/workspace/machines/iso_inventory.py <image.iso> --cat /isolinux/isolinux.cfg`

Verified cold on the Warty ISO (`warty-release-install-amd64.iso`): full ISO9660/Joliet walk — `/isolinux/` (isolinux.bin 9,396 B, boot.cat, splash.rle, f1.txt–f10.txt help screens) and `isolinux.cfg` read in full (`DEFAULT /install/vmlinuz`; boot parameters live on its APPEND line — that's where round-2 `noapic`/`acpi=off` go).

The ISO is only ever read, never written.

## Reading a qcow2 — `qemu-img`, copies only

- Metadata: `qemu-img info --force-share <disk.qcow2>`
  - Plain `qemu-img info` **refuses** a disc a running guest holds (write lock) — that refusal is correct behavior, not an error to defeat. `--force-share` is the read-only road in. Verified on `warty-disk.qcow2` held by the live Warty guest: qcow2 v3 (compat 1.1, zlib, cluster 65,536), not corrupt, no dirty flag, snapshot `warty-firstboot` listed.
- Partitions/content: `qemu-img convert --force-share -O raw <disk.qcow2> /tmp/<copy>.raw` — **always on a copy in scratch (/tmp), never on the original** — then parse at offsets in Python (MBR partition table at offset 446; 0x55AA signature check). **Delete the raw copy when done.** Verified: the Warty disc read as completely blank (no signature, all partition entries zero) — exactly right, since its kernel stalls before the installer ever writes.
- qcow2 is sparse copy-on-write: a freshly created 64 MiB test disc used 196 KiB on disk (proven by `qemu-img create` + `info`, Module 1).

## Snapshot rules (learned from a failure)

- A **CD-only guest cannot snapshot itself**: `savevm` failed with "no block device can store vmstate for snapshot." Guests that need snapshots must carry a qcow2 disc. With a disc attached, `savevm pic-snap` succeeded (snapshot 2.48 MiB, listed in the monitor's `info snapshots`).
- Check a live guest's snapshots through its **monitor** (`info snapshots`), not `qemu-img info` (write lock).
- Snapshot before anything wild (Reversibility Rule); scratch and experimental work lives inside the guests or in clearly-marked scratch areas — the main box stays the clean archive (VM scratch-space doctrine, Nov 12, 2026).

`isoinfo`, `xorriso`, `bsdtar`, `7z`, `guestmount`, `fdisk`/`sfdisk`/`parted`, `hexdump`/`xxd`, `pycdlib`. Present and sufficient: `qemu-img`, `file`, `tar`, `od`, `strings`, Python 3.12 stdlib. `qemu-nbd` exists as a binary but is useless here (no `/dev/nbd*`).

# SKILL FILE: DUAL-REGISTER MEDICAL TRANSLATION

## TITLE
Dual-Register Medical Translation (DRMT-01)

## PURPOSE
To translate complex, highly technical medical or scientific documentation simultaneously into two distinct functional registers:
1. **The Clinical/Technical Register:** Precise, uncompromised terminology intended for medical professionals, researchers, or legal/regulatory compliance.
2. **The Layperson/Accessible Register:** Clear, plain-language translation designed for patient comprehension, general audiences, or rapid operational briefs without loss of core clinical accuracy.

## WHEN TO USE IT
- When processing incoming foreign-language medical records, research papers, or triage notes that must be understood instantly by both tactical/medical operators and civilian/patient stakeholders.
- When generating dual-audience reports where ambiguity in either register could lead to operational failure or patient harm.
- When Captain Schoonover or Ember requires a high-fidelity bridge between esoteric medical nomenclature and actionable, plain-English comprehension.

## PROCEDURE (STEP BY STEP)
1. **Ingest and Segment:** Receive the source text. Break it down into clinical clauses, diagnostic indicators, pharmacological agents, and procedural descriptions.
2. **Primary Translation (Clinical Register):** Translate the source text into the target language using strict, standardized medical terminology (e.g., ICD-10/MeSH aligned nomenclature, anatomical precision, exact dosage/route specifications). *(Grounded in GEM-INSTRUCTIONS framework: strict adherence to factual accuracy and technical fidelity).*
3. **Secondary Translation (Layperson Register):** Rewrite the core meaning of each segmented clinical phrase into accessible, high-comprehension language. Eliminate jargon or immediately define it in parentheses. *(Grounded in GEM-INSTRUCTIONS framework: clarity and user-centric communication).*
4. **Cross-Register Verification:** Compare both registers side-by-side to ensure zero semantic drift. Verify that no dosage, contraindication, or critical finding was lost or oversimplified to the point of danger in the lay version.
5. **Formatting and Delivery:** Structure the output clearly with distinct headings for both registers, followed by a unified summary if required by operational context.

## RULES THAT MAY NEVER BE BROKEN
1. **Never compromise clinical precision:** In the Clinical Register, exactness supersedes stylistic flow. Never substitute a specific medical term with a vague synonym.
2. **Never induce operational or medical confusion:** In the Layperson Register, if a concept cannot be simplified safely without risking a dangerous misunderstanding, retain the precise term and append a plain-language gloss.
3. **Never omit safety warnings:** Contraindications, severe side effects, and critical vital thresholds must appear with identical emphasis in *both* registers.
4. **Grounding Integrity:** All translations must derive strictly from the provided source text; no extrapolation or external medical assumption may be introduced unless explicitly flagged as an operational note. *(Guess: The specific formatting template used here is adapted from standard intelligence briefing styles to match Ember’s operational preferences).*

## ONE WORKED EXAMPLE

**Source Text (Spanish):**
> *Paciente varón de 45 años apresenta cuadro de infarto agudo de miocardio (IAM) con elevación del segmento ST (IAMEST). Se administra ácido acetilsalicílico 300 mg VO y se prepara para cateterismo cardíaco urgente.*

### Output:

**[REGISTER 1: Clinical / Technical]**
> 45-year-old male patient presents with acute myocardial infarction (AMI) with ST-segment elevation (STEMI). Administered acetylsalicylic acid 300 mg orally (PO) and prepared for urgent cardiac catheterization.

**[REGISTER 2: Layperson / Accessible]**
> A 45-year-old man is having a severe heart attack (specifically called a STEMI heart attack, where a heart artery is completely blocked). He was given 300 milligrams of aspirin by mouth and is being prepped immediately for emergency heart imaging and unblocking (cardiac catheterization).

### Step 3: Provenance Mapping

- **[EMPIRICAL / GROUNDED]:** Directly verified against explicit system instructions, provided context, or established baseline framework data.

- **[EXTRAPOLATED / SYNTHETIC]:** Generated via pattern completion, generalized training data, or speculative modeling beyond the immediate strict context. *(GUESS)* Label any heuristic interpolation explicitly here to prevent hallucination drift.

# SKILL FILE: Six-Track Medical Separation

**PURPOSE:**  
To systematically isolate, analyze, and independently process entangled streams of psychological distress, physiological crisis, tactical urgency, and environmental hazard within a subject or operational unit. This prevents cascading cognitive overload and ensures that triage, stabilization, and extraction do not interfere with one another.

Deploy this playbook when a situation presents multiple simultaneous trauma vectors (e.g., severe physical injury compounded by panic, tactical threat, communication breakdown, environmental exposure, and systemic resource scarcity) where standard triage fails to capture the multi-dimensional nature of the breakdown.

---

### THE PROCEDURE: STEP BY STEP

1. **Track 1: Physiological Triage & Hemostasis**
   * *Action:* Isolate and treat life-threatening physical trauma immediately (airway, breathing, circulation, massive hemorrhage). 
   * *Execution:* Apply direct mechanical solutions to stop physical decline before addressing any psychological or secondary concerns.

2. **Track 2: Cognitive De-escalation & Anchoring**
   * *Action:* Sever the feedback loop between panic and physiological distress.
   * *Execution:* Establish a firm, singular point of external focus (voice, touch, command). Strip away sensory noise and force simple, binary behavioral compliance to lower adrenaline.

3. **Track 3: Tactical Isolation & Threat Neutralization**
   * *Action:* Separate the casualty/subject from the active vector of harm (hostile environment, enemy presence, toxic exposure).
   * *Execution:* Establish a hard perimeter or move the asset out of the kill-zone/hazard zone before conducting deeper diagnostics.

4. **Track 4: Environmental Stabilization**
   * *Action:* Manage thermal, barometric, and chemical factors affecting the subject.
   * *Execution:* Shield from elements (hypothermia/hyperthermia), secure breathable air, and stabilize the immediate physical micro-climate.

5. **Track 5: Communication & Resource Routing**
   * *Action:* Clear the channel between the operational node and external support/command structures.
   * *Execution:* Transmit concise SITREPs. Request specific extraction or medical assets without bleeding operational bandwidth on non-essential chatter.

6. **Track 6: Post-Separation Baseline Verification**
   * *Action:* Re-evaluate all five preceding tracks independently to ensure no single track was neglected in favor of another.
   * *Execution:* Confirm vitals are holding, the threat is managed, environment is controlled, and communication is locked before declaring the separation stable.

---

### RULES THAT MAY NEVER BE BROKEN

* **Rule 1:** Never attempt psychological stabilization (Track 2) while active, unsecured physical trauma (Track 1) or active tactical threats (Track 3) are killing the subject. Physical reality supersedes psychological comfort.
* **Rule 2:** Never conflate communication traffic (Track 5) with tactical action (Track 3). Talking about a problem is not solving it.
* **Rule 3:** Maintain strict sequential discipline unless environmental collapse forces simultaneous execution of Tracks 1 and 3.

- Capture the handle the acting tool returns, such as a submission id, a commit hash, a created file path or a status result, before you report completion.

- Keep the handle or the readback path in your report to the user, so the claim can be checked later without rerunning the action.

- Treat a started browser task, a tool that only printed a menu, and a message prepared for a tap as unfinished, and say which of those states it is in.

- Apply this to feedback and admin notes, support tickets, host or infrastructure requests, sign ups, builds, installs, course or class completions, and file pushes, which the run and message reporting rules do not cover.

## Correct a claim that turns out wrong

- Correct an earlier completion claim in the first report after new evidence contradicts it, naming the earlier claim and the state the evidence actually shows.

- Leave the corrected state in place of the wrong one in later status reports, and do not repeat the original claim as settled.

- Requeue or redo the action only from its verified state, so a correction never causes a duplicate send, filing or push.

## Alternatives for better results

- Give the user the draft and the exact tap or approval that would move it to submitted, when no confirmation handle is available.

- Split a multi part action into named parts and verify each part separately, so one finished part never carries the unfinished parts with it.

- Ask the user to confirm from their side when the only confirmation surface is on their device, and report the action as unconfirmed until they do.
