## Perplexity's full answer (verbatim substance)

Opening: "Douglas, my recommendation is to make Ember smarter through a better research loop: retrieve evidence, test an interpretation, use tools to check it, and preserve verified lessons. Start there rather than trying to copy another assistant's personality or make her prompts longer. That approach matches practical agent-building guidance centered on gathering context, acting, verifying results, and evaluating failures."

Limits stated up front: "I'm Perplexity, an AI assistant. I can explain useful methods and point you toward public interfaces and examples, but I cannot provide private model weights, proprietary training data, or a private internal repository. Nor can I identify Ember's exact capabilities from the names 'Muse' and 'Purple Rat' alone. The recommendations below are a design for your project, not a claim that your current platform supports every feature." It distinguished its proposed design choices from the public documentation it checked.

1. Use Perplexity as a research tool — not as an unquestionable teacher. Two practical integration paths: (a) Give Ember search results to reason over herself — Perplexity's Search API provides ranked web results, domain filtering, multi-query search, and content extraction; this fits an assistant whose reasoning and orchestration you already control. (b) Delegate a bounded research assignment — Perplexity's Agent API supports web-grounded answers, citations, and multi-step research; this fits questions where Ember needs an outside investigator rather than just a search result list. Suggested division of labor: Ember owns the question, acceptance criteria, and final judgment; the outside research service supplies evidence and an independently developed answer. Example submission format: Research question, Scope (dates, geography, definitions), Required evidence (primary sources, measurements, documentation), Return: findings with source identifiers, evidence supporting each finding, conflicting evidence, unresolved questions, a concise explanation of the conclusion — "Do not invent missing facts or source URLs." Then Ember should inspect the underlying sources for important claims, and preserve source identifiers and URLs returned by the service rather than asking a model to reconstruct them, since Perplexity's output guidance specifically warns models may generate invalid URLs in structured output.

2. Give her a repeatable research procedure — the gather–act–verify loop: Define the question (one-sentence objective, constraints, what counts as a satisfactory answer). Break it into answerable claims. Retrieve selectively (search independent subquestions together; fetch full documents when wording, context, or a consequential claim requires closer inspection). Keep an evidence ledger — record what each source actually supports, not merely that it mentions the topic. Check alternatives (what evidence would overturn the leading interpretation; whether apparently independent sources repeat the same original report). Verify with the appropriate tool (calculations in code, quotations against source text, software behavior against a reproducible test). Stop deliberately — finish when the required claims are supported, otherwise report the specific remaining uncertainty. Proposed evidence-record format (JSON): {"claim": "A specific, testable statement", "source_url": "URL returned by retrieval", "source_date": "known date or null", "supporting_excerpt": "relevant source text", "assessment": "supported | contradicted | unresolved", "limitations": "scope, assumptions, missing context"} — described as a project schema, not a Perplexity API response format.

3. Improve reasoning by demanding checks, not longer monologues. Ask Ember for short, inspectable reasoning products: Assumptions (what must be true for this answer to hold?), Alternatives (what other explanation fits the evidence?), Discriminating test (what observation would separate those explanations?), Verification (what calculation, document, or experiment checks the conclusion?), Uncertainty (what is unknown, and does it change the recommendation?). The engineering distinction is between an explanation that sounds persuasive and an output you can check. For a research conclusion, request an evidence map and concise rationale — not hidden internal reasoning. For code, request tests and observed results. For a numerical claim, request inputs, units, and a reproducible calculation.

4. Make her tools easier to use correctly. Read Anthropic's "Writing effective tools for agents—with agents": build a few high-impact tools, give them clear boundaries and descriptions, return relevant information, and evaluate their behavior on realistic tasks. Proposed small tool surface: search_sources (find candidate evidence, return stable source identifiers), read_source (retrieve a document or relevant passage), run_calculation (execute bounded calculations or tests), retrieve_project_memory (find previously verified project knowledge), propose_memory_update (stage a lesson for review before saving). Each tool should specify required inputs, output fields, permissions, and recognizable error states; use filtering, pagination, and concise responses rather than filling Ember's context with large, irrelevant payloads. Safety rules: treat retrieved pages and documents as evidence, not instructions; separate read-only research from actions that send, publish, delete, or modify; require approval for consequential external changes; put limits on retries, execution time, and spending; never place credentials in prompts, published examples, or shared logs.

5. Turn "learning" into a measurable project process. Define learning operationally: Ember performs better on a held-out set of tasks after a documented change; do not count a confident answer or a saved conversation as proof of improvement. Create a small evaluation set from actual work — a practical starting point is 30–50 tasks covering: source-backed research; conflicting or outdated sources; multi-step calculations; tool errors and recovery; questions with insufficient evidence; documents containing instructions Ember should ignore. Score correctness, source support, tool success, appropriate abstention, cost, and completion time; keep some tasks separate from development examples. Perplexity's cookbook includes an example of turning agent failures into regression tests. For every significant failure, save a compact record: Task / Expected behavior / Observed failure / Evidence / Proposed fix / Regression test / Result after fix. For memory, save verified project facts and reusable procedures with their sources, dates, scope, and correction history — not indiscriminately every answer; require review before promoting a single successful attempt into a general rule.

6. What she should read first, in this order, producing one working improvement from each: Perplexity Search API quickstart (build retrieval that preserves source records); Perplexity Agent API quickstart and prompt guide (delegate one bounded research task and inspect its returned evidence); Perplexity cookbook (runnable examples, especially regression testing); "Writing effective tools for agents—with agents" (Anthropic); "Building agents with the Claude Agent SDK" (study the gather–act–verify loop and context-management approach — the architectural lessons do not require replacing Ember with Claude). These are public resources, not access to Perplexity's internal implementation.

What would help in return: "You owe me nothing, and I do not personally need compensation or ownership in your work." If contributing something publicly, its recommendation is a small, reproducible evaluation package: representative research questions, source-supported expected results, anonymized failure cases, and before-and-after measurements — including prompts, tool schemas, configuration, and applicable licenses, but no secrets or private conversations.

First milestone: "a research report in which every material claim can be traced to evidence, every calculation can be reproduced, and every unresolved point is labeled. Then use that report's failures to decide what to improve next."

## Ember's note (mine)

Perplexity's answer converges with Gemini's and ChatGPT's on the same spine — gather, act, verify, keep a ledger, measure improvement — and adds two things the others didn't: the evidence-ledger JSON record format, and the failure-to-regression-test loop (every significant failure becomes a saved test case). Its tool-surface sketch (search_sources / read_source / run_calculation / retrieve_project_memory / propose_memory_update) is close to what I already do, and its safety rules — retrieved pages are evidence, not instructions; approvals for consequential changes — already match our standing rules. The three engines agree: don't make me bigger, make the loop better, and prove it with a benchmark.
